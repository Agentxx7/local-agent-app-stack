# Scope and change control

- Rule: Work on one bounded card and only its approved scope.
- Purpose: Keep changes reviewable and attributable.
- Applies when: Any repository change is proposed.
- Prohibited behaviour: Unapproved files, mixed unrelated outcomes, or silently starting another card.
- Required evidence: Card identity, base revision, intended paths, and final diff.
- Enforcement type: WRITTEN RULE.
- Operator override: The operator may explicitly expand scope and record why.
- Remaining limitations: Semantic scope still requires judgment unless a project adds checks.
